# Requirements Table – Alumni Mentorship & Mock Interview Platform

The table below follows the lab template: **Req ID, Type, Description, Priority, Acceptance Criteria, Rationale, Comments**.

## Functional Requirements

| Req ID | Type | Description | Priority | Acceptance Criteria | Rationale | Comments |
|---|---|---|---|---|---|---|
| **FR-001** | Functional | **The system shall recommend alumni mentors to students based on domain matching and mentor availability, and shall support one-click session booking.** | High | **Pass:** For a student selecting a supported domain, the system displays at least one matching available mentor when one exists; selecting an available slot allows the student to proceed to booking. **Fail:** No matching/available mentor is shown when a qualifying mentor exists. | Core functionality for connecting students with suitable alumni. | Given by instructor; retains the scenario's domain-matching and one-click booking focus. |
| **FR-002** | Functional | **The system shall allow a student to view an alumni mentor's domain expertise, profile information, and available session slots before booking.** | High | **Pass:** Selecting a mentor displays the mentor's expertise and available slots. **Fail:** The student cannot view the required information before booking. | Helps students choose an appropriate mentor before committing to a session. | Derived from FR-001's mentor-matching context and availability requirement. |
| **FR-003** | Functional | **The system shall allow a student to book an available mentorship session and add the confirmed session to both the student and mentor calendars with a meeting link.** | High | **Pass:** After booking an available slot, one calendar event is created for each participant, the slot becomes unavailable, and a meeting link is attached. **Fail:** Any required booking artifact is missing or the same slot remains bookable. | Directly supports the core mentorship-booking workflow. | Acceptance criteria explicitly checks the sample requirement's double-booking condition. |
| **FR-004** | Functional | **The system shall allow a student to schedule a mock interview with an available alumni mentor for a selected time slot.** | High | **Pass:** A selected available slot creates a mock-interview appointment and meeting link and marks the slot unavailable. **Fail:** The appointment is created without an available slot or the slot remains available afterward. | Enables the mock-interview service described in the problem statement. | Derived from the platform title and post-interview scorecard requirement. |
| **FR-005** | Functional | **The system shall allow an alumni mentor to record structured feedback and a scorecard after a completed mentorship or mock interview session.** | Medium | **Pass:** After a completed session, the mentor can submit feedback and scores, and the submitted record is available to the student. **Fail:** Feedback cannot be submitted or the student cannot view a submitted scorecard. | Provides structured post-session evaluation for student improvement. | Directly supports the scenario's structured post-interview scorecard recording. |

## Non-Functional Requirements

| Req ID | Type | Description | Priority | Acceptance Criteria | Rationale | Comments |
|---|---|---|---|---|---|---|
| **NFR-001** | Nonfunctional | **The system shall protect all user profile and feedback scorecard data according to applicable privacy guidelines and shall support soft-deletion of requested data within 24 hours.** | High | **Pass:** Privacy/security checks confirm authorized access, and an approved deletion request is soft-deleted within 24 hours. **Fail:** Unauthorized access is possible or the deletion target is not soft-deleted within 24 hours. | Profile and feedback information can contain sensitive personal data. | Given by instructor's NFR guideline; combines its privacy and 24-hour soft-deletion requirements. |
| **NFR-002** | Nonfunctional | **The system shall prevent double-booking and maintain booking consistency during concurrent session-booking requests.** | High | **Pass:** In a concurrency test where two students attempt the same final available slot, exactly one booking succeeds and the other receives an unavailable-slot response. **Fail:** Both requests create confirmed bookings for the same slot. | Prevents conflicting appointments and protects calendar correctness. | Derived from the sample FR acceptance criterion: “Fail: Double-booking of mentor slots.” |
